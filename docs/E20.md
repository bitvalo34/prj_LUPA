# E20 — Transporte y flujo LUPA

## Estado actual

E20 está en cierre sobre `feature/e20-transport`. Los bloques funcionales cubren WebSocket, sesión, planificación uniforme, TILE binario, créditos, RELEASE y DONE. Las pruebas de robustez de E20 están automatizadas; la última verificación manual debe ejecutarse en el WSL de Erwin antes de pasar el PR a revisión.

## Bloque 1 — WebSocket RFC 6455

Implementado:

- `GET /lupa` con Upgrade WebSocket.
- versión WebSocket 13.
- subprotocolo obligatorio `lupa.v1`.
- validación de Key, Upgrade, Connection y Origin.
- opción `--ws-allow-no-origin=true|false`.
- respuesta 101 completa antes del handoff del socket.
- conservación de bytes recibidos después de las cabeceras HTTP.
- parser incremental para lecturas parciales o múltiples frames por lectura.
- máscara obligatoria para cliente → servidor.
- longitudes 7/16/64 bits con validación de codificación mínima.
- rechazo de RSV/opcodes reservados.
- texto WebSocket fragmentado y UTF-8 validado sobre el mensaje reconstruido.
- ping/pong y cierre básico con timeout.
- cola de escritura serializada, acotada y compatible con escrituras TCP parciales.

Los controles de aplicación binarios enviados por el cliente se rechazan. Las extensiones WebSocket no se negocian.

## Bloque 2 — Sesión y controles LUPA

Estados por conexión:

```text
ESPERA_HELLO -> LISTA -> IMAGEN_ABIERTA -> CERRADA
```

### HELLO / WELCOME

HELLO requerido:

```json
{"type":"HELLO","version":1,"windowBytes":1048576,"bitmapBudgetBytes":67108864}
```

WELCOME:

```json
{"type":"WELCOME","version":1,"windowBytes":1048576,"maxTileBytes":262144,"maxInFlight":16}
```

La ventana negociada queda entre 512 KiB y 1 MiB. Una versión LUPA distinta de 1 produce `VERSION_UNSUPPORTED`. Una ventana inferior al mínimo produce `LIMIT_EXCEEDED`.

### OPEN / MANIFEST

OPEN:

```json
{"type":"OPEN","epoch":1,"imageId":"demo-auxiliar"}
```

El servidor resuelve el catálogo publicado mediante `PublishedImageStore`, fija esa `imageVersion` inmutable para la apertura y responde MANIFEST con dimensiones y niveles reales.

Una imagen inexistente produce `IMAGE_NOT_FOUND`. Una entrada publicada cuyo catálogo/manifiesto no pueda resolverse de forma consistente produce `IMAGE_NOT_READY`.

### VIEW / PLAN temporal de E20

E20 acepta de momento únicamente:

- `mode="uniform"`.
- `detailOffset=0`.
- `focus=null`.

Las variantes de foco y offsets pertenecen al refinamiento de E21 y por ahora reciben `BAD_VIEW`; no se ignoran silenciosamente.

Ejemplo:

```json
{
  "type":"VIEW",
  "epoch":2,
  "imageId":"demo-auxiliar",
  "imageVersion":"v1",
  "rect":{"x":0,"y":0,"width":1096,"height":815},
  "viewportPx":{"width":800,"height":600},
  "detailOffset":0,
  "mode":"uniform",
  "focus":null
}
```

PLAN:

```json
{"type":"PLAN","epoch":2,"appliedLevel":3,"contextLevel":3}
```

El nivel se selecciona como el menor nivel cuya densidad de píxeles puede cubrir simultáneamente el ancho y alto físicos del viewport para la región solicitada. Si ningún nivel inferior alcanza la densidad solicitada, se usa el máximo publicado.

El rectángulo usa coordenadas de la imagen original y debe quedar completamente contenido. El viewport se limita a 8,294,400 píxeles.


## Bloque 3 — TILE, región real, créditos, RELEASE y DONE

### Selección espacial

Para cada VIEW uniforme se crea un cursor perezoso; no se materializa una lista completa de teselas.

1. se emite primero la tesela \`z=0, x=0, y=0\` como miniatura;
2. después se recorren únicamente las teselas del nivel aplicado que intersectan el rectángulo;
3. si el nivel aplicado es \`z=0\`, la miniatura no se duplica;
4. los intervalos se tratan como semiabiertos, por lo que un borde alineado exactamente con una frontera de tesela no agrega la tesela vecina.

La conversión de región usa las dimensiones exactas publicadas de cada nivel.

### Lectura publicada

\`PublishedTileReader\` resuelve rutas únicamente mediante \`PublishedImageStore\`, lee como máximo 262144 bytes y valida:

- firma JPEG;
- decodificación real mediante ImageIO;
- ancho/alto esperados, incluidas teselas de borde;
- coherencia con el manifiesto publicado.

La lectura se ejecuta fuera de callbacks NIO. Cada sesión mantiene como máximo una lectura activa por plan y como máximo una tesela leída esperando crédito, evitando cargar una pirámide o plan completo en memoria.

Una lectura tardía vuelve a comprobar la generación del plan antes de enviar datos. Si el VIEW/OPEN fue sustituido, el resultado se descarta.

### Sobre binario TILE

Cada TILE es un mensaje WebSocket binario independiente:

\`\`\`text
4 bytes H (big-endian)
H bytes JSON UTF-8
payload JPEG
\`\`\`

La cabecera contiene:

\`\`\`json
{
  "type": "TILE",
  "deliveryId": 1,
  "epoch": 2,
  "imageId": "demo-auxiliar",
  "imageVersion": "v1",
  "z": 0,
  "x": 0,
  "y": 0,
  "w": 137,
  "h": 102,
  "codec": "jpeg",
  "payloadBytes": 4133
}
\`\`\`

Reglas:

- H <= 4096.
- payloadBytes <= 262144.
- longitud exacta = 4 + H + payloadBytes.
- \`deliveryId\` es por conexión y no se reinicia al cambiar epoch o imagen.
- identidad de caché sigue siendo imageId + imageVersion + z + x + y.

### Créditos y RELEASE

La ventana libre se inicializa al valor negociado en HELLO.

Antes de encolar un TILE se reserva exactamente:

\`\`\`text
4 + H + payloadBytes
\`\`\`

No se incluyen bytes del frame WebSocket en la reserva.

Además se limita a 16 entregas pendientes por conexión. Si no hay ventana o cupo, la sesión pausa el plan pero continúa aceptando controles como RELEASE.

RELEASE válido:

\`\`\`json
{"type":"RELEASE","deliveryId":1,"status":"discarded"}
\`\`\`

Estados aceptados:

\`\`\`text
displayed
discarded
failed
\`\`\`

El servidor recupera el tamaño reservado desde su propio registro. Un RELEASE duplicado o desconocido se ignora y no crea crédito. Una entrega de una época anterior todavía pendiente puede liberarse normalmente.

Invariante mantenido:

\`\`\`text
ventana libre + suma de reservas pendientes = ventana negociada
\`\`\`

### DONE

\`sentTiles\` cuenta TILE completamente escritos al socket, no TILE mostrados ni liberados.

DONE se encola solamente después de que se haya completado la escritura del último TILE del plan vigente:

\`\`\`json
{"type":"DONE","epoch":2,"sentTiles":21}
\`\`\`

No se emite DONE para un plan sustituido ni para un plan que termina con \`INTERNAL_READ_ERROR\`.


## Política de épocas fijada para E20

- epoch está en 1..2147483647.
- OPEN o VIEW válidos deben usar una época mayor que la intención vigente.
- una época menor o repetida se ignora y no crea trabajo.
- una solicitud inválida no avanza la época ni modifica el estado válido.
- cambiar imagen o época no reiniciará deliveryId ni créditos cuando éstos se conecten al bloque TILE/RELEASE.
- OPEN válido reemplaza la imagen/plan previo.
- VIEW válido reemplaza el plan previo.

## JSON y transiciones inválidas

Los controles usan JSON UTF-8 y se validan con detección estricta de campos duplicados, tokens sobrantes, profundidad, tamaño de cadenas, cantidad de campos y tipos.

Los errores de aplicación que pertenecen al contrato se devuelven mediante `ERROR`. Un JSON malformado, tipo desconocido o transición de estado imposible no tiene un código ERROR v1 específico; E20 lo trata como violación de política WebSocket y cierra con 1008 en lugar de inventar un código nuevo.

## Probe independiente de Java 21

Con el servidor usando datos reales:

```bash
java -jar target/lupa.jar \
  --host=127.0.0.1 \
  --port=8081 \
  --data-root=/home/erwin/PRJIMA/data
```

ejecutar:

```bash
java -cp target/lupa.jar gt.lupa.tools.LupaControlProbe \
  ws://127.0.0.1:8081/lupa \
  demo-auxiliar \
  /home/erwin/PRJIMA/data
```

Debe observarse:

```text
WebSocket OPEN; subprotocol=lupa.v1
WELCOME ...
MANIFEST demo-auxiliar/v1 ...
PLAN ...
TILE delivery=... sha256=...
...
DONE epoch=2 sentTiles=...
E20 TILE/RELEASE probe completed successfully.
```

Este cliente es deliberadamente independiente de A20. Decodifica el sobre TILE, valida longitud y JPEG, calcula SHA-256, compara longitud/hash con el JPEG publicado cuando se proporciona data-root, envía RELEASE con estado `discarded` y comprueba DONE.

## Cierre y evidencia

Ya están automatizados en E20:

- dos conexiones WebSocket reales con créditos y deliveryId independientes;
- desconexión abrupta durante salida binaria y recuperación del accept loop;
- desconexión mientras existe una lectura de tesela pendiente;
- archivo que desaparece entre PLAN y la lectura de disco;
- handshake + primera trama en el mismo write TCP;
- fragmentación de texto, UTF-8 dividido y ping intercalado;
- longitudes 7/16/64, máscara, close, mensajes binarios de cliente rechazados y escrituras parciales;
- regresiones de HTTP y catálogo;
- build online y offline en CI.

La integración de A20 está documentada en `docs/A20-E20-integration.md`. La matriz de criterios está en `docs/E20-closure.md`.

Antes de cambiar el PR de borrador a listo para revisión, Erwin debe sincronizar el HEAD final, ejecutar `mvn -o clean verify package` y repetir `LupaControlProbe` sobre `demo-auxiliar`.

E21/E22 siguen siendo responsables del refinamiento completo de foco/detailOffset, navegación rápida avanzada, heartbeat y robustez/carga global.
