# E19 — Base HTTP asíncrona de LUPA

## Alcance

E19 implementa la base Maven/Java 21, servidor HTTP/1.1 acotado con NIO.2, recursos locales, catálogo compatible con `docs/contrato-v1.md`, fixture temporal y pruebas. No implementa WebSocket funcional, visor, planificador, créditos, épocas ni transmisión de teselas.

## Arquitectura entregada

- `gt.lupa.LupaApplication`: punto de entrada.
- `gt.lupa.config.ServerConfig`: configuración y límites.
- `gt.lupa.http.NioHttpServer`: aceptación y conexiones con `AsynchronousServerSocketChannel`/`AsynchronousSocketChannel`.
- `gt.lupa.http.HttpParser`: subconjunto HTTP/1.1 deliberado.
- `gt.lupa.http.HttpRouter`: rutas públicas explícitas.
- `gt.lupa.http.AsyncWritePump`: escritura serializada y continuación de escrituras parciales.
- `gt.lupa.storage.CatalogSource`: interfaz acordada con S19.
- `ClasspathCatalogSource`: fixture temporal de E19.
- `FileCatalogSource`: punto de integración con catálogo/manifiestos publicados por A19.

Las lecturas potencialmente bloqueantes de recursos/catálogo se realizan en un executor de trabajo acotado, no en callbacks NIO.2.

## Subconjunto HTTP soportado

Rutas: `GET|HEAD /`, `/assets/app.css`, `/assets/app.js`, `/api/catalog` y `/lupa`. En E19 `/lupa` responde `501 Not Implemented` y nunca `101`.

Política: solo HTTP/1.1; `Host` obligatorio y único; GET/HEAD sin cuerpo; `Content-Length: 0` aceptado; otras longitudes, `Transfer-Encoding`, Content-Length duplicado o encuadre ambiguo se rechazan; `Connection: close`; sin keep-alive ni pipelining; HEAD conserva cabeceras GET sin cuerpo; cabeceras case-insensitive; query separada antes del enrutamiento.

Códigos: `200`, `400`, `404`, `405`, `408`, `431`, `501`, `503`, `505` según el caso documentado en pruebas.

## Protección

No existe ruta genérica al sistema de archivos. Solo se sirven recursos classpath explícitos. Se rechazan `..`, `.` codificado, backslash, separadores codificados, porcentajes inválidos y UTF-8 inválido. No hay listados ni rutas públicas a originales, staging, pirámides, configuración, logs o `.git`. `FileCatalogSource` valida identificadores y no sigue symlinks para JSON.

## Configuración inicial

- host `127.0.0.1`
- puerto `8080` (`0` permitido en pruebas)
- catálogo `fixture`
- catálogo real `data/catalog.json`
- cabeceras 16 KiB
- conexiones 128
- timeout cabeceras 5000 ms
- cola trabajo 256
- recurso web 1 MiB
- JSON catálogo/manifiesto 256 KiB

Argumentos: `--host`, `--port`, `--catalog=fixture|file`, `--catalog-path`, `--max-header-bytes`, `--max-connections`, `--header-timeout-ms`.

## Fixture E19

`src/main/resources/fixtures/catalog.json` y `lupa-small-v1-manifest.json` son datos de prueba, no una importación real. Mantienen el contrato S19 (`lupa-small`, `v1`, 4096×3072, tile 256, niveles 0..4). Para integrar A19: `--catalog=file --catalog-path=data/catalog.json`.

## Preparación con Internet

```bash
java -version
mvn -version
rm -rf .m2-offline
mvn -Dmaven.repo.local=.m2-offline dependency:go-offline
mvn -Dmaven.repo.local=.m2-offline clean verify package
```

El segundo ciclo real es obligatorio: `dependency:go-offline` por sí solo no prueba que todos los artefactos estén disponibles.

## Validación sin Internet

```bash
mvn -o -Dmaven.repo.local=.m2-offline clean verify package
java -jar target/lupa.jar --host=127.0.0.1 --port=8080 --catalog=fixture
```

Luego verificar con `curl` `/`, CSS, JS, `/api/catalog` y `curl -I /`. Los recursos web no contienen CDN, fuentes remotas ni servicios externos. Maven `-o` valida Maven offline; la prueba final debe repetirse con conectividad física deshabilitada.

## Pruebas automáticas

`mvn verify` cubre GET/HEAD, MIME, Content-Length, fixture/manifiesto, 404/405, fragmentación, cabeceras grandes/incompletas, Host, Content-Length/Transfer-Encoding, traversal/codificación inválida, dos clientes, timeout, desconexión, escrituras parciales deterministas, cierre tras respuesta y ausencia de segunda respuesta por pipelining. CI repite `mvn -o`, arranca el JAR y consulta rutas locales.

## Integración A19/I19

Adrian puede publicar `data/catalog.json` y `data/pyramids/<imageId>/<imageVersion>/manifest.json` con el esquema de `docs/contrato-v1.md`. E19 consume mediante `FileCatalogSource`; no conoce libvips ni rutas de originales/staging. I19 sigue pendiente hasta probar el catálogo real.
