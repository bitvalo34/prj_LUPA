# A22 — Ingreso y revisión funcional

## Objetivo y estado

A22 valida el recorrido funcional que sigue a A19, A21, I21 y E22:

- publicar una segunda imagen sin reiniciar el servidor;
- publicar una nueva versión inmutable del mismo `imageId`;
- demostrar que una importación fallida no reemplaza el catálogo anterior;
- completar mensajes de error, reconexión y telemetría del visor;
- dejar instrucciones reproducibles y evidencia de frontend y memoria.

La implementación y las pruebas automatizadas están preparadas. La evidencia manual con
una imagen autorizada del equipo debe completarse en `docs/evidencias/A22.md` antes de
marcar la tarea como cerrada.

La campaña de 100 cambios corresponde a A23, no a A22.

## Semántica de publicación y versiones

El catálogo mantiene una sola versión vigente por `imageId`, pero las versiones ya
publicadas permanecen inmutables en disco.

1. La primera importación de `imagen-a` publica `v1`.
2. Otra importación con el mismo `imageId` publica la siguiente versión disponible.
3. El catálogo pasa a apuntar a la versión nueva y conserva los demás `imageId`.
4. Una sesión que ya abrió `v1` permanece fijada a `v1`.
5. Un `OPEN` posterior, aun en el mismo WebSocket, obtiene la versión vigente.

El visor no cambia de versión silenciosamente. Después de recargar el catálogo muestra
`Nueva versión disponible`; la lectura activa sigue identificada en el readout
`VERSIÓN`. Al pulsar nuevamente el cartucho se envía un `OPEN` nuevo.

## Cambios del visor

- Una recarga fallida de `/api/catalog` conserva la última lista válida y muestra un
  aviso recuperable.
- Los seis códigos `ERROR` de LUPA se presentan en español con una acción sugerida.
- Un cierre WebSocket anormal muestra código, motivo y la acción `Reconectar`.
- Seleccionar una imagen sin conexión ya no muestra falsamente el estado `Lista`.
- Al cambiar rápidamente de imagen se cancelan las reservas RGBA antiguas de inmediato;
  sus callbacks siguen vivos únicamente para cerrar el bitmap y emitir el `RELEASE`
  correspondiente.
- La telemetría incluye TILE fallidos, `DONE.sentTiles` y balance de TILE
  contabilizados/recibidos.
- La traza A22 incorpora un encabezado con imagen, versión, conexión, época,
  contadores, pendientes y bytes de bitmaps administrados.

Los contadores siguen siendo acumulativos por conexión. Un `OPEN` no reinicia los
`deliveryId` ni los totales; para comparar dos imágenes se toman los valores antes y
después. `Reconectar` sí crea una conexión nueva y reinicia sus contadores.

## Preparación

Desde la raíz del repositorio en WSL:

```bash
java -version
mvn -version
node --version
npm --version
vips --version
vipsheader --version
```

Requisitos:

- Java 21;
- Maven 3.9.x (Maven 3.8.x es rechazado por el `pom.xml`);
- Node.js 20.19.0 o posterior y npm compatible con `package-lock.json`;
- libvips disponible localmente;
- una fotografía JPEG pequeña, propia o autorizada, para la validación. No hace falta
  usar una imagen de 40–80 GB en A22.

Construcción completa:

```bash
cd frontend
npm ci
npm test
npm run build
cd ..
mvn -o clean verify
```

## Validación aislada del importador

El script usa un directorio temporal, un puerto independiente y una sola instancia del
servidor. No modifica el `data-root` normal:

```bash
bash scripts/verify-a22.sh /ruta/absoluta/foto-autorizada.jpg
```

Verifica automáticamente:

- `a22-primary/v1`;
- `a22-secondary/v1` publicada mientras el servidor sigue activo;
- reimportación de `a22-primary` como `v2`;
- conservación física de `v1` y `v2`;
- catálogo HTTP con ambas imágenes y la versión vigente;
- importación JPEG inválida con código distinto de cero;
- SHA-256 de `catalog.json` idéntico antes y después del fallo.

Para conservar el directorio temporal y el log:

```bash
KEEP_A22_RUN=1 bash scripts/verify-a22.sh /ruta/absoluta/foto-autorizada.jpg
```

## Validación manual en el visor

Usar el `data-root` normal y mantener el servidor en una terminal:

```bash
export LUPA_DATA_DIR="$HOME/lupa-data"

java -Xms256m -Xmx2g -XX:+ExitOnOutOfMemoryError \
  -jar target/lupa.jar \
  --host=0.0.0.0 \
  --port=8081 \
  --data-root="$LUPA_DATA_DIR"
```

En otra terminal, importar una fotografía pequeña con un `image-id` nuevo:

```bash
java -cp target/lupa.jar gt.lupa.ingest.IngestApplication import \
  --original="/ruta/absoluta/segunda.jpg" \
  --image-id=a22-segunda \
  --display-name="A22 segunda imagen" \
  --license-ref="Fotografía propia o autorizada para la prueba A22" \
  --data-root="$LUPA_DATA_DIR" \
  --vips=vips \
  --vipsheader=vipsheader \
  --timeout-seconds=600 \
  --jpeg-quality=85
```

Sin reiniciar Java:

1. Pulsar `Recargar catálogo`.
2. Abrir la imagen nueva y volver a la anterior.
3. Confirmar que el número de conexión no cambia y que las épocas sí aumentan.
4. Repetir la importación con `--image-id=a22-segunda` para crear la siguiente versión.
5. Recargar catálogo: el cartucho anuncia una versión nueva, pero el readout conserva
   la versión abierta hasta volver a pulsar el cartucho.
6. Al estabilizarse, comprobar `Decodificando=0`, `Por pintar=0`, balance TILE exacto
   y `RELEASE = Dibujados + Descartados + Fallidos` para la conexión completa.
7. Detener y volver a iniciar el servidor. Pulsar `Reconectar`; debe aumentar
   `Conexión`, reiniciar contadores y reabrir la selección conservada.
8. Guardar la traza A22 y una captura con imagen, versión y telemetría visibles.

## Fallo de importación sobre el data-root normal

No se debe corromper el catálogo deliberadamente. Basta usar una entrada inválida y
comparar el catálogo antes/después:

```bash
sha256sum "$LUPA_DATA_DIR/catalog.json"
printf 'no es jpeg\n' > /tmp/lupa-a22-invalid.jpg

java -cp target/lupa.jar gt.lupa.ingest.IngestApplication import \
  --original=/tmp/lupa-a22-invalid.jpg \
  --image-id=a22-fallo \
  --display-name="A22 fallo esperado" \
  --license-ref="Fixture local inválida" \
  --data-root="$LUPA_DATA_DIR" \
  --vips=vips \
  --vipsheader=vipsheader \
  --timeout-seconds=60 \
  --jpeg-quality=85

echo "exit=$?"
sha256sum "$LUPA_DATA_DIR/catalog.json"
curl -fsS http://127.0.0.1:8081/api/catalog
```

El comando de importación debe fallar, ambos hashes deben coincidir y el visor debe
seguir utilizando el catálogo anterior. El fallo pertenece a la herramienta CLI; no
existe ni se necesita una API de importación en el navegador.

## Memoria en un equipo de 16 GB

`-Xms256m -Xmx2g` es una configuración prudente para esta validación. No es necesario
aumentar `-Xmx` por el tamaño del original: el servidor entrega teselas y no carga la
imagen completa en memoria.

Por defecto, E22 limita explícitamente la caché JPEG comprimida a 128 MiB y los
envelopes TILE fuera de caché a 16 MiB. Cada visor administra hasta 64 MiB de bitmaps,
con 16 MiB reservados para contexto y trabajo transitorio. Estas cifras no incluyen
todo el heap Java, memoria nativa, GPU, buffers del sistema operativo ni procesos del
navegador.

Con 16 GB se puede ejecutar el servidor y uno o dos navegadores para A22. No se
recomienda modificar `.wslconfig`, aumentar el heap ni abrir 20 clientes antes de medir
un problema real; la carga de 1/5/20 clientes corresponde a E23/E24.
