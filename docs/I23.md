# I23 — Versión funcional integrada

Responsable: **Erwin Arevalo**  
Fecha de preparación en repositorio: **3 de octubre de 2026**.

I23 depende de A23 y E23. Este documento no declara el cierre por anticipado: el workflow de aceptación debe demostrar que ambas dependencias y el recorrido integrado corresponden al mismo commit candidato.

## Puertas de dependencia

Antes de considerar I23 completa se exige:

- A23 con campañas de 100 cambios y 100 ciclos sobre navegador real;
- E23 repetida sobre el mismo HEAD mediante `scripts/e23/verify-e23-final.sh`;
- build frontend/backend compatible y empaquetado en `target/lupa.jar`;
- catálogo con imágenes publicadas por el importador real;
- ausencia de defectos bloqueantes detectados por la aceptación.

El workflow `.github/workflows/a23-i23-acceptance.yml` ejecuta estas puertas en ese orden y conserva evidencia en un único artefacto.

## Recorrido integrado cubierto

El recorrido automatizado usa el frontend de producción compilado dentro de los recursos Java y el servidor empaquetado. La campaña abre catálogo real, selecciona una imagen importada, negocia WebSocket `lupa.v1`, procesa HELLO/WELCOME, OPEN/MANIFEST, VIEW/PLAN, TILE reales, Worker, Canvas, confirmaciones selectivas, DONE, navegación, detalle, foco, cambio de imagen y reconexión.

La sonda A23 también registra solicitudes HTTP/WS y falla si observa una solicitud externa. El workflow solicita una ruta de originales y exige que no sea servida con HTTP 200.

Después de la importación inicial, el servidor se mantiene en un único proceso para las pruebas de navegador. La evidencia del importador prueba además publicación válida y conservación del catálogo ante una importación inválida.

## Cliente lento y cliente activo

I23 reutiliza las pruebas ya implementadas en E22/E23 y las repite sobre el commit candidato:

- `LupaSessionFairnessTest`: sesión lenta frente a otra que continúa progresando;
- `LupaSessionTimeoutTest`: expiración de entregas no confirmadas;
- `NioHttpServerSlowWebSocketTest`: cliente que no lee del socket;
- `LupaSessionReconnectCleanupTest`: limpieza y nueva conexión independiente.

Estas pruebas mantienen separadas las condiciones «no confirma RELEASE/ACK» y «no lee del socket»; no se tratan como un único escenario.

### Estado de `ACK_STATE`

La documentación técnica ya incorpora la evolución posterior del control selectivo: `ACK_STATE` es el mecanismo que ejerce actualmente el navegador y `RELEASE` se conserva en el servidor por compatibilidad de LUPA v1. I23 no necesita inventar un cambio de contrato; debe comprobar que el informe final, los ejemplos y la implementación permanezcan consistentes con esa semántica real.

## Freeze de funciones

Al pasar A23/I23 no se incorporan funciones nuevas. El trabajo siguiente queda limitado a:

- defectos y regresiones;
- evidencia y mediciones;
- actualización del documento del protocolo;
- empaquetado y demostración.

Una función obligatoria ausente continúa siendo bloqueante; el freeze no permite retirar requisitos para declarar la integración aprobada.
