# E23 — Pruebas backend y medición

Responsable: **Erwin Arevalo**  
Fecha de trabajo: 23–25 de septiembre de 2026.

E23 endurece el backend de LUPA mediante pruebas repetibles de HTTP, WebSocket, protocolo LUPA, créditos, cancelación, saturación y recuperación. También incorpora un cliente de carga real en Java 21, escenarios reproducibles y una baseline experimental sin cancelación para preparar la campaña formal de E24.

La confirmación de entregas sigue siendo RELEASE. E23 no introduce un mensaje ACK nuevo.

## Alcance implementado

### Errores HTTP y WebSocket

La batería E23 reutiliza y amplía las pruebas existentes para cubrir cabeceras parciales, EOF prematuro, timeout y recuperación del accept loop; parser HTTP; rutas privadas y traversal; admisión; handshake WebSocket; máscara obligatoria; RSV; longitudes; fragmentación; segundo mensaje durante fragmentación; límite acumulado; heartbeat; cola de escritura y timeout de progreso.

### RELEASE, épocas y créditos

Se añadió cobertura para JSON malformado y campos duplicados, HELLO incompleto, solicitudes fuera de estado, épocas reemplazadas, RELEASE con displayed/discarded/failed, RELEASE duplicado, deliveryId desconocido, entrega antigua pendiente, RELEASE antes del callback final de escritura, callback tardío y desconexión mientras I/O puede completar.

En las transiciones cubiertas se comprueba:

    freeWindowBytes + reservedBytes = negotiatedWindowBytes

El cambio de época no reinicia créditos y un RELEASE duplicado no devuelve bytes dos veces.

### Saturación, aislamiento y recuperación

E23 cubre con límites reducidos y pruebas deterministas: cliente que agota su ventana por no liberar crédito, otro cliente que sigue progresando, límite de sesiones y admisión posterior al cleanup, cola de disco llena y recuperación, cola de turnos de lectura llena y recuperación, cliente que no lee, timeouts, reconexión y buffers transitorios acotados.

### Cliente de carga real

gt.lupa.tools.E23LoadClient usa el cliente WebSocket estándar de Java 21 y establece sesiones reales HELLO/WELCOME → OPEN/MANIFEST → VIEW/PLAN → TILE → RELEASE discarded → DONE.

El cliente mantiene estado independiente por sesión, deriva recorridos del manifiesto real, reconstruye callbacks fragmentados, valida TILE/JPEG, nunca reporta displayed, emite VIEW por calendario temporal sin esperar DONE, registra trabajo obsoleto y conserva JSONL, CSV y JSON por ejecución.

Los bytes informados son bytes de aplicación LUPA/JPEG, no bytes exactos TCP/WebSocket.

### Baseline experimental sin cancelación

La baseline solo se habilita al arrancar el servidor mediante propiedades JVM y está desactivada por defecto. No añade mensajes experimentales al protocolo público.

Los planes aceptados se conservan en una cola FIFO acotada; al saturarse se responde LIMIT_EXCEEDED. El cliente sigue descartando TILE obsoletas y enviando RELEASE.

## Preparación E24

E23 deja preparados los runners cold/warm, normal/no-cancel, 1/5/20 clientes y cinco repeticiones por condición. cold significa JVM nuevo/caché de aplicación vacía; no implica vaciar la page cache del sistema operativo. warm usa un único JVM y una corrida de calentamiento no medida.
