## Comandos

### Preflight

```bash
java -cp target/lupa.jar gt.lupa.ingest.IngestApplication preflight \
  --original="/ruta/privada/foto.jpg" \
  --image-id=sample-photo \
  --display-name="Sample photo" \
  --license-ref="Fotografía propia; permiso confirmado" \
  --data-root=data
```

### Staging diagnóstico

```bash
java -cp target/lupa.jar gt.lupa.ingest.IngestApplication stage \
  --original="/ruta/privada/foto.jpg" \
  --image-id=sample-photo \
  --display-name="Sample photo" \
  --license-ref="Fotografía propia; permiso confirmado" \
  --data-root=data \
  --jpeg-quality=85
```

`stage` no publica catálogo; sirve para inspeccionar una pirámide antes de la publicación completa.

### Importación completa

```bash
java -cp target/lupa.jar gt.lupa.ingest.IngestApplication import \
  --original="/ruta/privada/foto.jpg" \
  --image-id=sample-photo \
  --display-name="Sample photo" \
  --license-ref="Fotografía propia; permiso confirmado" \
  --data-root=data \
  --vips=vips \
  --vipsheader=vipsheader \
  --timeout-seconds=600 \
  --jpeg-quality=85
```

## Política de imagen

- Entrada admitida: JPEG y TIFF detectados por el loader real de libvips.
- TIFF multipágina: rechazado cuando `n-pages > 1`.
- Orientación: `vips autorot`.
- Color: sRGB.
- Alpha: fondo blanco `(255,255,255)` antes de JPEG.
- Original: copia privada, inmutable, verificada por SHA-256.
- Calidad JPEG inicial: 85, configurable 40–95.
- Teselas: 256 × 256 máximo, `overlap=0`, `depth=onetile`.

## Layout

```text
data/
  catalog.json
  originals/
    <imageId>/<imageVersion>/
      source.jpg | source.tiff
      import-metadata.json
  staging/
    .ingest.lock
    job-.../
  pyramids/
    <imageId>/<imageVersion>/
      manifest.json
      tiles/<z>/<x>_<y>.jpg
```

`originals`, `staging` y `pyramids` son privados y no se exponen como rutas HTTP.

## Publicación

1. Preflight e inspección.
2. Estimación conservadora de espacio.
3. Lock exclusivo del importador.
4. Generación en staging.
5. Validación completa de manifiesto y teselas.
6. Copia privada del original y SHA-256.
7. Movimiento atómico de la versión completa a `pyramids`.
8. Validación del catálogo anterior.
9. Reemplazo atómico de `catalog.json`.
10. Limpieza únicamente del staging del trabajo.

Una versión publicada no se sobrescribe. Si el catálogo falla después de mover una versión completa, el catálogo anterior continúa válido y puede quedar una versión completa no referenciada para recuperación manual.

## Integración con E19 / I19

E19 consume:

- `data/catalog.json`;
- `data/pyramids/<imageId>/<imageVersion>/manifest.json`.

La ruta interna de una tesela es:

```text
data/pyramids/<imageId>/<imageVersion>/tiles/<z>/<x>_<y>.jpg
```

La validación final confirmó que E19 puede servir mediante `/api/catalog` el catálogo generado por A19. Esto demuestra compatibilidad, pero **I19 sigue pendiente como tarea de integración formal**.
